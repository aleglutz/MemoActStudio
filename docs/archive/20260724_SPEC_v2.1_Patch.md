# SPEC v2.1 — review decisions and amendments

**Date:** 2026-07-24 · **Applies to:** `SPEC.md` (v2), `ALIGNERS.md`
**Status:** decided by project lead; apply to the spec and proceed.

---

## 0. Priority principle (new — governs everything below)

**A working end-to-end PoC beats portability.** Where a choice is between shipping a working reel sooner and keeping the install light, offline-capable, or maximally portable — choose the working reel. Portability and offline deployment are **September hardening tasks with their own checklist**, not gates on the July prototype.

Consequence: do not let install weight, model size, or offline-install concerns block or slow any implementation decision now. Note them in a `HARDENING.md` checklist and move on.

## 1. Decision — acceptance criterion §6.8 (amended)

The original wording ("no model downloads") conflated two things: GPU/diffusion dependency (which we genuinely exclude) and any model file at all (which was never the intent). Correct reading applied:

**Replace §6.8 with:**

> 8. The Branch A graph runs on a plain local ComfyUI install with **no GPU-class or diffusion checkpoints**. The aligner's speech model is permitted — **no size ceiling**; select whatever the bake-off shows to be accurate enough, preferring the smaller model only where accuracy is equal. Presence of a GPU is neither required nor harmful.

**Moved to `HARDENING.md` (September offline workshop, not a PoC gate):**

- `nodes_align.py` accepts an explicit local model path (no forced auto-download at runtime).
- Documented offline install: model directory copied from USB; 16 participants must not download the model simultaneously over museum Wi-Fi.
- Bake-off question, informational only: does `base` (~145 MB) suffice, or is `small` (~484 MB) needed? We measure timing accuracy, not transcription quality, so the smaller model may well be enough — but **do not compromise PoC accuracy to find out**.

## 3. Decision — stable-ts confirmed as primary, behind an interface

Confirmed. Reasoning accepted: `align()` performs exactly our operation (known text + audio → timings) with no sequence-matching layer for us to write and maintain, and torch already ships with ComfyUI so the dependency increment is small.

**Requirement — the interface matters more than the engine.** Define the protocol first and build `nodes_align.py` against it immediately; do **not** wait for the bake-off to start coding.

```python
# memoacts_core/align.py
class Aligner(Protocol):
    def align(self, audio_path: Path, blocks: list[str], lang: str) -> list[Span]: ...
# Span: {index: int, t_start: float, t_end: float, confidence: float, estimated: bool}
```

`StableTsAligner` is the first implementation. `WhisperXAligner` / `MmsFaAligner` are alternative implementations if the bake-off justifies them. Swapping engines must touch one file, never the node layer. The bake-off runs **in parallel with** implementation, not before it.

## 4. Scope correction — Armenian is off the critical path

**Alignment runs only for the language of the narration.** Translated subtitle tracks (DE, FR, HY, RU) inherit shot boundaries from that single alignment — they are block-matched translations timed to the same shots (§5.5), not independently aligned audio.

Narration languages in scope: **RU** (Sidur reference project) and **EN** (course). Nothing else is required.

Consequence: **drop `MMS_FA` from the bake-off** unless it is free to include. Its selling points were 1100+ languages and Armenian coverage — neither is on the critical path, and both came with costs (uroman romanisation, digit expansion, NC weights). Armenian alignment becomes relevant only if a participant later narrates in Armenian for their own project; note it in `HARDENING.md` and stop there.

Bake-off is therefore: **stable-ts (primary) vs. whisperx (accuracy benchmark)**, on RU + EN.

Armenian still matters for **rendering**: font coverage and libass shaping must be verified (existing backlog item, unchanged).

## 5. New requirement — text normalisation pre-pass (engine-independent)

Add to §5.1. This is not an aligner choice; every candidate needs it.

> **Normalisation before alignment.** Digits, dates and abbreviations must be expanded to spoken form before the text is handed to the aligner — "1974" → «тысяча девятьсот семьдесят четвёртом», "18" → «восемнадцати». The normalised text is used **for alignment only**; the verbatim script is what reaches the screen and the `.srt`/`.ass` files.
>
> Russian requires case and number inflection, so a bare `num2words` call is insufficient — evaluate the approach and document it. Mis-normalisation must degrade gracefully: a block that fails to align falls back to proportional timing with `estimated: true`, never a failed run.

Rationale: this is the dominant error class in historical content and it is exactly what the reference material contains — the Sidur script carries dates in roughly every second sentence (1974, 1979, 1941, 1970-е). Unexpanded digits are where alignment will drift, regardless of engine.

---

## 6. New requirement — shot lead

Add to §5.1 / §5.2:

> Shot cuts lead the sentence onset by a configurable `shot_lead_ms` (suggested default 80–120 ms), exposed as a widget. An image appearing fractionally early reads as intentional; an image appearing late reads as a mistake.

Cheaper than chasing the last milliseconds of aligner accuracy, and it gives the creator a control rather than a fixed behaviour.

---

## 7. Working method note

`SPEC.md` is not authoritative on verifiable facts. v1 listed `aeneas` as the preferred aligner; the survey correctly established it as a dead end (2017, C extension + eSpeak, Windows/py3.11 install hostile, AGPL). **Anything in the spec marked "verify" or "evaluate" is a hypothesis to test, not an instruction to follow.** Continue exactly this pattern — surfacing a contradiction is a deliverable, not a delay.

## 8. Open question for the project lead (answer before PoC target is fixed)

The priority principle above says the cloud PoC comes first — but there is a structural tension to resolve, not paper over:

**`comfyui-memoacts` cannot be installed on Comfy Cloud** (curated node list only, §3). So "a working PoC in the cloud" can mean one of:

- **(a)** PoC runs locally on the project lead's own ComfyUI (custom pack, full functionality); "cloud" applies to Branch B teaching graphs only.
- **(b)** PoC is assembled on Comfy Cloud from **stock/Cloud-supported nodes only**, accepting reduced functionality, so that intensive participants can run it in the same environment they are being taught in. `SURVEY.md`'s Cloud-coverage findings determine how much of Branch A this can cover.
- **(c)** PoC runs on a **self-hosted cloud instance** (full custom-node control, participants get a URL), with cost and administration implications.

This choice changes what gets built first. Flag it to the project lead and wait for the answer before fixing the PoC target.
